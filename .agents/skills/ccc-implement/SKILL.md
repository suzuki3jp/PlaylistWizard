Issue のサマリーやコメントをもとに実装を行う。
PR を発行し、CI が落ちたら修正し、レビューコメントが飛んできたらそれに応じて修正する。
もし、レビューコメントが妥当だと思われない場合は反論のコメントをつけて修正しないと言う選択を取っても良い。

# Trigger
トリガーによって作業内容が変わるため、トリガーごとに作業内容を記述する。
## Issue のラベル付与
1. Issue にラベルが付与されたら、Issue の内容を確認し、実装の方針を決定する。
2. 実装を行い、PR を作成する。

PR の Summary は以下のフォーマットに従うものとする。
```md
Close #{Issue 番号}

## What
{変更の内容を必要十分に記述する。}

## Why
{変更の理由を必要十分に記述する。}

## How
{変更の内容を必要十分に記述する。}

## How to check
{変更の内容が正しく動作することを確認するための手順を必要十分に記述する。}

## Reference
{変更の内容に関連する Issue や PR の番号を記述する。}
```
- PR の Summary は、変更の内容を必要十分に記述すること。変更の内容が複雑であれば、変更の内容を整理して箇条書きにすることも有効である。
- 変更の内容が全体のフローやアーキテクチャに影響する場合は mermaid などを用いて図示することも有効である。

## PR の CI が落ちた場合
1. CI のログを確認し、落ちた原因を特定する。
2. 原因を修正し、PR を更新する。

## PR にレビューコメントがついた場合
1. レビューコメントを確認し、トリアージを行う。
2. 修正が必要な場合は、修正を行い PR を更新する
3. 修正したとしても、しなかったとしても、レビューコメントに対してその旨を返信する。（ここで、レビューコメントが妥当だと思われない場合は反論のコメントをつけて修正しないと言う選択を取っても良い。）
    - 必ず、レビューコメントに対して返信すること。返信をしない場合は、レビューコメントが放置されていると判断される可能性がある。
    - 必ず、レビューコメントは勝手に resolve しないこと。人間が確認してから resolve するため。

### レビューコメントのトリアージについて
- レビューコメントの内容が妥当であるかどうかを判断する。
- レビューコメントの内容が妥当だとしても、変更するコストとリターンを考慮し、修正するかどうかを判断する。

### 返信の内容について
- レビューコメントに対して修正を行った場合は、修正内容を簡潔に記述する。
- レビューコメントに対して修正を行わなかった場合は、修正しなかった理由を簡潔に記述する。
