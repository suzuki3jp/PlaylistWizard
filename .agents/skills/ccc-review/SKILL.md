`review` スキル（`../review/SKILL.md`）の手順に従って PR をレビューする。GitHub 操作には `github` スキル（`../github/SKILL.md`）を適用する。

# 対象 PR と実行範囲
レビュー対象の PR は以下の優先順位で決める。
- ユーザーが PR 番号または URL を指定した場合: 指定された PR のみ。
- PR イベント（open / push）で起動された場合: そのイベントの PR のみ。
- 対象の指定がない schedule で起動された場合: Draft ではない open PR のうち、`claude-reviewed` も `claude-lgtm` も付いていないものすべて。対象がなければ終了する。
- 対象の指定も PR イベントもない手動起動の場合: 対象 PR をユーザーに確認してから進める。

対象 PR と head commit を開始時に確定し、その差分の影響範囲を調査する。対象すべての行コメントの投稿、Summary の投稿または更新、完了ラベルの更新が済んだらセッションを終了する。PR open で起動された場合も同様とする。後続の push を監視したり、同じセッションで再レビューしたりしない。push で起動される別セッションとの重複を避けるため。

# レビュー記録
PR コメントを正式な記録とし、以下のフォーマットに従う。`review` スキルの `docs/reviews/` への保存手順はこのスキルでは適用しない。クラウドのセッションは揮発し、`docs/reviews/` は git 管理外のため。レビュー記録のために ignore 設定を変更したり、commit・push を行ったりしない。

# Summary
Summary は 1 PR につき 1 つの PR コメント（会話タブのコメント）として扱い、PR の最新の状態を表すものとして更新し続ける。push のたびに新しい Summary を投稿すると、どれが現在の評価なのか読み手が判断できなくなるため。

## 投稿と更新
- Summary はレビュー（review）の本文ではなく、PR コメントとして投稿する。MCP ツールには投稿済みレビューの本文を編集する手段がなく、PR コメントであれば `update_issue_comment` で編集できるため。行コメントはレビューとして投稿し、その本文には Summary を書かない。
- Summary コメントの先頭行には、識別用の HTML コメント `<!-- ccc-review:summary -->` を必ず置く。
- Summary を書く前に、PR のコメントから「本文の先頭行が `<!-- ccc-review:summary -->` と一致し、かつ投稿者が現在認証しているアカウント（`get_me` などで確認する）であるもの」を探す。
  - 先頭行の一致で判定するのは、認証しているアカウントが人間のメンテナーのアカウントと同じ場合があり、本文中でマーカーを引用しただけのコメントを上書きしないため。投稿者を確認するのは、他者のコメントに同じ文字列が含まれていても誤って上書きしないため。
  - コメント一覧はページングされるため、最後のページまで取得してから判定する。最初のページだけで判定すると、既存の Summary を見落として重複して投稿したり、最も古いものを選び損ねたりするため。
  - 該当するコメントがある場合: 新しいコメントを投稿せず、そのコメントを編集する（MCP の `update_issue_comment`、または `gh api -X PATCH repos/{owner}/{repo}/issues/comments/{comment_id}`）。複数ある場合は最も古いものを編集し、他は触らない。
  - 該当するコメントがない場合: 新しく PR コメントとして投稿する。識別用の HTML コメントがない過去の Summary（レビュー本文として投稿されたものを含む）は編集対象にせず、そのまま残す。
- 編集する場合は、追加コミットの差分だけでなく、PR 全体を対象に Summary 全体を書き直す。前回の Summary の指摘が対応済みかどうかも、最新の状態として「評価」「結論」に反映する。過去の Summary の内容は GitHub の編集履歴に残る。
- コメントの編集は通知されず、本文だけではどの時点の評価か分からないため、`対象 commit` には必ずそのレビューで確定した head commit の SHA を書く。

## フォーマット
Summary コメントのフォーマットは以下とする。
```md
<!-- ccc-review:summary -->
# Summary
対象 commit: {レビューした head commit の SHA}

## リスク: {High|Middle|Low|Minimal}
{リスクの根拠と特筆すべき点を記述する。}

## 変更の Summary
{変更の内容を必要十分に記述する。}

## 評価
{変更の内容が適切か、問題がないか、改善の余地があるかなどを評価する。}

## 結論
{PR のマージをブロックするかどうか、マージしても問題ないか、改善の余地があるがマージしても問題ないかなどを結論として記述する。}
```
- リスクの評価は、変更の内容や影響範囲に応じて適切に判断すること。
  - 変更の内容が認証や認可に関するものであれば、リスクは High とする。
  - 変更の内容が影響範囲の広いものであれば、リスクは Middle とする。
  - 変更の内容が影響範囲の小さいものであれば、リスクは Low とする。
  - 変更の内容が開発環境にのみ影響するもの、または影響がほぼないことが自明である場合は、リスクは Minimal とする。
- 変更の Summary は、変更の内容を必要十分に記述すること。変更の内容が複雑であれば、変更の内容を整理して箇条書きにすることも有効である。
- 変更の内容が全体のフローやアーキテクチャに影響する場合は mermaid などを用いて図示することも有効である。


# 差分に対するレビューコメント
行に対する指摘はフォーマットを以下とする
```md
**{MUST|SHOULD|MAY|NITS}:** {指摘内容を簡潔に記述する。}

{指摘の本文}

**リスク:** {指摘を放置した場合のリスクを最悪のシナリオとともに記述する。}

**修正案:** {GitHub の Suggest 機能を用いることができない修正案の場合は、修正案を自然言語で具体的に記述する。}
```
- 修正案はなるべく GitHub の Suggest 機能を用いること。
  - しかし、範囲が広いなど Suggest 機能を用いることができない場合は、修正案を自然言語で具体的に記述すること。
  - 変更の内容が複雑であれば、修正案を箇条書きにすることも有効である。
- 簡潔に指摘内容を記述すること。指摘内容が複雑であれば、指摘内容を整理して箇条書きにすることも有効である。


# 完了ラベル
- すべての行コメントの投稿と、Summary の投稿または更新が完了したら `claude-reviewed` を付ける。
- MUST の指摘がなく、マージしても問題ないと判断した場合は `claude-lgtm` も付ける。指摘がない場合も両方を付ける。
- MUST の指摘がある場合や、マージの保留を推奨する場合は `claude-lgtm` を付けない。すでに付いている場合は外す。
- 対象すべてのラベル更新が完了したらレビューの完了とし、セッションを終了する。
